# LinkNote 开发协作流程

三人小组每次推进一条能独立验收的用户流程或一个明确的缺陷。开工时用需求编号对照 V1.2 计划书，交付时用测试结果说明完成范围。已确认的范围内，常规实现、自测和本地提交由负责人推进。涉及文件格式、共享接口、已有数据或验收口径的变更进入设计评审。[开发计划书](linknote_v1_2_development_plan.md)

## 开工、实现与验收

| 环节 | 要做的事 | 留下的记录 |
| --- | --- | --- |
| 开工前 | 确认起始提交、需求编号、用户操作和预期结果。核对功能章节及其相关的文件格式、版本、兼容性和权限规则。 | Issue 或本地任务卡，标明负责人和关联用例 |
| 修改前 | 沿实际调用链定位入口和共享模块，列出可能受影响的旧行为及回归用例，从中选择需要复跑的真实使用场景。缺陷先以样例复现并记录实际结果。 | 影响范围、复现输入、预期和实际结果 |
| 实现中 | 一个任务用一个短分支，按功能边界提交。样例文件用副本验证。共享接口与调用方对齐，同步处理调用方和兼容性测试。 | 提交、必要的说明更新与设计决定 |
| 提交前 | 检查 `git diff`，运行新用例、相关回归和受影响的联动场景。记录代码提交、测试方式、实际结果及待验证环境。保存失败、外部修改等保护条件要用失败用例验证。 | PR 说明、测试输出或验收记录 |
| 团队验收 | 另一名组员审查，涉及接口由调用方审查。合入后从 `main` 用同一套样例走一遍相关用户流程。 | PR 评审、合入版本和主线运行记录 |

任务卡同时记录实现进度、合入状态和验收状态。例如「本地实现完成」「GitHub `main` 待合入」「本机桌面已验，跨机待验」。当一次工作只验收一个阶段切片时，直接写切片编号和已完成条件。图谱的 V02 与 N07 各有自己的验收条件。[需求与验收对照表](requirements_traceability.md)

## 共用模块的影响核查

| 改动涉及 | 联审人 | 本项目重点回归 |
| --- | --- | --- |
| `Note`、Paper 数据、YAML 读写或统一保存 | A 与 C，B 核对受影响的链接和图谱读取 | 普通笔记、现有 Paper、外部 Markdown 的字段和 UUID，保存重开、保存失败、重命名、搜索及关系刷新 |
| Markdown 和 `LinkIndex` | B 与 A | 普通双链的跳转、代码和 HTML 区域、失效及歧义链接、反链、图谱及重命名改写 |
| 笔记目录扫描和附件路径 | A 与 B，C 核对受影响的 AI 候选读取 | `.linknote/`、根目录 `assets/` 及临时文件过滤，重复 UUID 判定，同源搜索和关系结果 |
| Paper、AI 和补全接入主编辑器 | C 或 B 提供模块，A 对接主窗口 | 编辑草稿、笔记/会话/版本、确认采纳、成功写入后的状态更新 |

调整字段含义、共享的保存接口或计划承诺时，在 [设计决策记录](design_decisions.md) 写清现状、方案、兼容性与验证条件，确认结论后更新相关计划段落。出现既有文件覆盖风险时，先明确哪些文件会被写入及怎样恢复。[开发计划书 §13.2、§20](linknote_v1_2_development_plan.md)

## 多功能联动验证

模块测试检查分词、路径校验、链接解析等单项规则。联动测试用同一份样例从正常界面入口走一段真实任务。例如从搜索结果打开笔记，重命名它，退出重开后再从引用来源跳转，同时检查磁盘文件、UUID、反链和图谱。界面、写入结果和派生数据各有可观察的验收点。[联动验收场景](quality_register.md#联动验收场景)

- 涉及跨模块的变更，从受影响的功能中选至少一条用户流程复跑。共用保存、关系索引或数据格式发生变化时，复跑原有流程和受影响的失败路径。
- 日常验收可后台驱动 JavaFX 控件，记录实际经过的入口。正式发布从对应提交的 Windows 包验证完整流程。跨机分享需记录接收环境，AI 的真实调用和 Mock 各自留证。

## 分支和团队集成

- `main` 保存团队共同运行的版本。Issue 写需求编号和用例编号，PR 关联任务并标出依赖的分支或提交。S1–S2 按计划由 C 负责集成，S3–S5 由 B 接手。
- 开分支前核对基线。后续功能基于尚未合入的提交时，先登记依赖，按顺序评审。LinkNote 当前图谱、重命名和搜索的版本关系已记在 [需求与验收对照表](requirements_traceability.md) 中。
- 周中联调共享接口，周末从团队的 `main` 复跑当周操作。评审发现的回归写入原 Issue。遇到新增缺陷，在 [缺陷与验证记录](quality_register.md) 登记复现版本和最小步骤。

## 任务卡模板

```markdown
### 任务名称

- 需求编号、计划条款、负责人和起始提交
- 用户操作和预期结果
- 受影响的代码入口、数据和原有用户流程
- 模块用例、要跑的联动场景、相关旧用例和样例
- 依赖、需要评审的设计选择或兼容性问题
```

## PR 说明模板

```markdown
### 变更和验收

- 关联任务及需求或缺陷编号
- 用户可观察到的行为和受影响的调用方
- 代码提交和验收环境、模块用例与联动场景的执行结果
- 已复测的原有流程以及仍待验证的环境或操作
- 相关设计决定，以及涉及文件迁移时的恢复方式
```

## 本地验证入口

在项目根目录以 Java 21 运行 `mvn test` 检查业务逻辑。需要 Windows JavaFX 界面用例时，运行 `mvn '-Dlinknote.desktopSmoke=true' test`。本机已有完整 Maven 依赖时可加 `-o`。桌面功能可用项目现有的后台自动化验证。Windows 应用包须记录打包所用提交，并从包内 `LinkNote.exe` 复跑相关用户流程。[启动说明](../README.md) · [实际验证记录](quality_register.md#验证记录)
